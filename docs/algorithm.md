# 합류 지점 추천 알고리즘

설계는 기획서 §5와 design.md §8에 있습니다. 이 문서는 **구현에서 정한 세부 사항**을 기록합니다. 코드는 `backend/app/optimization/`에 있습니다.

## 처리 순서

| 단계 | 파일 | 내용 |
|---|---|---|
| 1 | `engine.py` | 차량별 기본 경로 조회 → `T_base`, 폴리라인 |
| 2 | `windows.py` | 만남 목적으로 합류 시간대 계산 |
| 3 | `candidates.py` | 시설·경로 근접·방향 필터, 간이 점수로 상위 K개 |
| 4 | `engine.py` | 매트릭스 조회 → `T_to`, `T_after` |
| 5 | `scoring.py` | 지표 계산 |
| 6 | `engine.py` | 영업·우회 한도·시간대 필터 |
| 7 | `scoring.py` | 정규화 목적함수, 정렬 |
| 8 | `engine.py` | TOP 3, 목적지 비교, 안내 문구 |

## 구현에서 정한 값

계획서에 값이 없어 초기값을 정한 항목입니다. 모두 `backend/.env`로 바꿀 수 있습니다.

| 항목 | 값 | 이유 |
|---|---|---|
| `DEPART_TOGETHER`의 ε | 1.2 | 계획서는 "ε를 높여"라고만 함. 기본값의 2배 |
| 시간대 확장 폭 | ±30분, 1회 | 계획서는 "범위를 넓혀"라고만 함 |
| 간이 점수 | 직선 우회 km + 시간대 밖 분 | 시간대 밖 후보가 상위 K개를 차지하지 않도록 함 |
| 장소 항목 무시 기준 | 범위 0.05 미만 | 3분 기준은 시간 항목에만 해당 |
| 재추천 변경 제안 기준 | 그룹 지연 합 5분 이상 개선 | 기획서 F06의 "충분한 개선" |
| 지연 판단 기준 | 계획보다 10분 이상 늦음 | 기획서 F06의 "일정 수준" |
| 응답 초과 시 K 감소 | ×0.7, 최소 5 | design.md §8.5 |

## 측정 시각 처리

`arrival(i,p) = 측정 시각(i) + T_to(i,p)`로 절대 시각을 구합니다. 위치의 측정 시각이 달라도 도착 시각을 같은 기준으로 비교합니다.

## 장소 부적합도 `q`

```text
q = 1 − (0.5·주차 + 0.2·식당 + 0.15·EV충전 + 0.1·화장실 + 0.05·매점)
주차 = min(주차면수 / 200, 1)
```

주차면수가 없으면 0.3으로 두고 `data_uncertain`을 표시합니다. 공통 목적지의 `q`는 0입니다. 어차피 가는 곳이기 때문입니다.

## 진행 방향 판단

1. 휴게소 이름의 괄호에서 진행 방향 도시를 읽습니다. `문막(강릉)`은 강릉 방향입니다.
2. 휴게소에서 그 도시로 향하는 방위각을 구합니다.
3. 차량 경로에서 휴게소와 가장 가까운 지점의 진행 방위각을 구합니다. 앞뒤 1.5km 구간으로 곡선의 영향을 줄입니다.
4. 두 방위각의 차이가 90도 미만이면 같은 방향입니다.

경로가 2km 안으로 지나가는 **모든** 차량이 같은 방향이어야 합니다. 경로가 멀리 있는 차량은 방향을 따지지 않고, 도로 경로 시간에서 생기는 우회로 걸러집니다.

**원본의 상행/하행을 쓰지 않는 이유:** 일부 노선에서 값이 뒤섞여 있습니다. 예를 들어 중앙선에는 `(하행, 부산)`과 `(상행, 부산)`이 함께 있습니다.

**한계:** 도시 방향으로 판단하므로 진행 방향 도시 근처나 크게 굽은 구간에서 틀릴 수 있습니다. 영동선 14곳은 실제 도로 형상으로 맞게 판정되는 것을 확인했고, 다른 노선은 실험 결과로 점검이 필요합니다.

## 후보 시설

`일반휴게소`만 후보입니다. `간이휴게소`는 단시간 정차용이고 `화물차휴게소`는 승용차 합류에 맞지 않아 제외합니다.

## 시간대의 기준 시각

"출발 후 90~150분"의 출발 시각은 **그룹이 처음 합류 장소를 고른 시각**입니다. 재추천과 목적지 변경에도 같은 값을 씁니다. 그 전에 대기실에서 추천을 미리 보는 동안에는 요청 시각을 기준으로 계산합니다.

## 추천 결과의 구성

- 후보와 목적지를 함께 정렬해 앞의 3개를 `recommendations`로 보냅니다.
- 목적지가 TOP 3 밖이어도 `destination_comparison`에 항상 들어갑니다. 기획서 F03 표의 "비교 기준" 행입니다.
- 목적지가 1위면 안내 문구를 넣습니다.
- 합류 장소가 이미 정해진 뒤의 재추천은 `change_recommended`로 변경 권장 여부를 알립니다. 합류 지점을 자동으로 바꾸지 않습니다.
- 현재 합류 지점은 비교하려고 지표를 계산하지만, 방향·시설·우회·시간대 조건을 통과해야 추천 대상이 됩니다. 조건을 통과하지 못하면 유지를 권하지 않고 변경을 권장합니다.

## 전기차: 기다리는 시간을 충전 시간으로

`optimization/ev.py`. 위치와 함께 배터리 잔량을 보낸 차량에만 적용합니다.

```text
사용량(%)      = 경로 시간 × 80km/h × 0.18kWh/km ÷ 77.4kWh × 100
도착 잔량      = 현재 잔량 − 사용량(T_to)
목적지 잔량    = 도착 잔량 − 사용량(T_after)
충전 필요      = 목적지 잔량 < 예비 20%
충전 시간(분)  = (예비 20% + 사용량(T_after) − 도착 잔량) × 77.4kWh ÷ 100kW × 60   (80%까지)
겹침           = min(충전 시간, 그 차량의 대기 시간)
추가 대기      = 충전 시간 − 겹침            (충전기 있음)
               = 충전 시간 + 따로 들르는 10분  (충전기 없음, 또는 합류 지점까지도 못 감)
```

목적함수에 두 가지를 반영합니다.

- **대기 항목**은 `총 대기 − 겹침`으로 계산합니다. 충전하며 기다린 시간은 버리는 대기가 아니기 때문입니다.
- **ζ·정규화(추가 대기)** 항을 더합니다(ζ=1.0). 추가 대기는 충전이 가장 오래 걸리는 차량 기준이며, 그룹 지연 합에는 차량 수만큼 곱해 넣습니다. 모두가 그만큼 더 기다리기 때문입니다.

배터리 값이 없으면 겹침과 추가 대기가 모두 0이라 점수는 이전과 같습니다(`tests/test_ev.py`).

**정한 값:** 배터리 용량·전비·평균 속도·충전 출력은 중형 전기 SUV 기준 초기값이며 `.env`(`EV_BATTERY_KWH`, `EV_KWH_PER_KM`, `EV_CHARGER_KW`, `EV_RESERVE_PERCENT`, `EV_CHARGE_LIMIT_PERCENT`)로 바꿀 수 있습니다. 차량 SDK가 차량별 용량을 알려 주면 그 값으로 바꾸는 것이 다음 단계입니다. 휴게소의 충전기 여부는 공공데이터(`has_ev_charger`)이고 실시간 빈자리는 반영하지 않습니다.

## 목적지 없는 드라이브: 코스 고르기

`services/free_drive.py`.

1. 위치를 공유 중인 차량들의 중심에서 직선거리 × 1.3 ÷ 70km/h로 왕복 시간을 어림해, 목표에 가까운 명소 40곳만 남깁니다(경로 조회량 제한).
2. 차량 × 명소 도로 시간 행렬을 한 번 조회합니다. 왕복 시간 = 2 × 차량별 편도 시간의 평균.
3. 목표 ±15분 안의 명소 중 이번 드라이브에서 보여 주지 않은 곳을 무작위로 고릅니다. 모두 보여 줬으면 직전 코스만 빼고 다시 섞습니다.
4. 범위 안에 없으면 목표와 가장 가까운 곳을 고르고 그 사실을 안내합니다.
5. 야경 테마인데 도착 예상 시각이 해 지기 전(서울 월별 대략값)이면 그 시각을 안내합니다.

고른 명소는 일반 목적지와 똑같이 합류 지점 추천에 쓰입니다.
